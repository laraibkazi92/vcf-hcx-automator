This guide outlines the workflow, data requirements, and logical steps to build a CLI tool for automating the addition of Virtual Machines (VMs) to **VMware HCX Mobility Groups (version 4.11)**.

This document is intended for an **LLM Coding Agent** that has access to the official VMware HCX Swagger/OpenAPI documentation. Use this as the architectural blueprint.

---

# Automation Blueprint: HCX Mobility Group CLI Tool

## 1. Objective
Build a CLI utility that ingests a CSV file containing VM details and orchestrates the creation (or update) of an HCX Mobility Group to migrate those VMs.

**Target Version:** VMware HCX 4.11
**Key Concept:** In HCX 4.x, migrations are managed via **Mobility Groups** (collections of VMs migrated together) rather than individual migration workflows.

---

## 2. Input Data Requirements (CSV)
The CLI should accept a CSV file. Since the HCX API requires internal IDs (MoRefs), the CSV will primarily contain human-readable names which the tool must resolve.

**Recommended CSV Headers:**
| Header | Description | Example |
| :--- | :--- | :--- |
| `vm_name` | Name of the VM in vCenter | `app-web-01` |
| `mobility_group` | Name of the Mobility Group to create or add to | `Wave-1-Finance` |
| `migration_type` | Type of migration | `bulk` (or `vmotion`, `rav`, `cold`) |
| `dest_network` | Name of the target network segment | `db-segment-1` |
| `dest_datastore` | Name of the target datastore | `vsanDatastore` |
| `dest_folder` | (Optional) Target folder path/name | `Finance/Web` |
| `dest_compute` | (Optional) Target cluster/resource pool | `Cluster-01` |
| `upgrade_tools` | (Optional) Boolean to upgrade VM tools | `true` |
| `remove_isos` | (Optional) Boolean to remove ISOs | `true` |

---

## 3. API Workflow & Logic

The agent should implement the following sequence of operations.

### Step 1: Authentication (Session Management)
*   **Action:** Authenticate to the HCX Manager (Source) to obtain an access token.
*   **Endpoint:** `POST /hybridity/api/sessions`
*   **Headers:** `Content-Type: application/json`
*   **Body:** `{ "username": "...", "password": "..." }`
*   **Output:** Extract the `x-hm-authorization` token from the response headers. This token must be included in the header of all subsequent requests.

### Step 2: Site Pairing & Service Mesh Retrieval
Before looking up VMs, the tool needs the context of the remote site.
*   **Action:** Get the active Site Pairing and Service Mesh IDs.
*   **Endpoint:** `/hybridity/api/interconnect/site/systems` (or similar `site-pairs` endpoint).
*   **Logic:**
    1.  List connected sites.
    2.  Select the destination site (pass as CLI argument or define in config).
    3.  **Critical:** Store the `siteId` (Source) and `remoteSiteId` (Destination).

### Step 3: Inventory Resolution (Name -> ID Mapping)
The API cannot accept "app-web-01"; it requires `vm-402` (MoRef ID). The tool must resolve these names.

*   **Action:** Query the inventory to map CSV string values to HCX internal IDs.
*   **Endpoint:** `/hybridity/api/interconnect/site/inventory` (Use query parameters for filtering).
*   **Logic:**
    *   **Source VMs:** Query source inventory filtering by `primaryName` matching `vm_name` from CSV.
        *   *Capture:* `inventoryId` (e.g., `vm-123`), `resourceId`, and `computerResource` details.
    *   **Destination Network:** Query destination inventory (using `remoteSiteId`) for `dest_network`.
        *   *Capture:* `inventoryId` (e.g., `dvportgroup-55`).
    *   **Destination Datastore:** Query destination inventory for `dest_datastore`.
        *   *Capture:* `inventoryId` (e.g., `datastore-10`).
    *   **Destination Compute:** Query destination inventory for `dest_compute`.
        *   *Capture:* `inventoryId`.

> **Note to Agent:** If a name is ambiguous (duplicates found), the tool should error out or prompt the user.

### Step 4: Create or Retrieve Mobility Group
*   **Action:** Check if the `mobility_group` specified in the CSV exists.
*   **Endpoint:** `GET /hybridity/api/mobility-groups` (Filter by name).
*   **Logic:**
    *   If **Exists**: Get its `id`.
    *   If **Not Exists**: Call `POST /hybridity/api/mobility-groups`.
        *   **Payload:** Requires `name`, `sourceId` (Source Site ID), and `destinationId` (Remote Site ID).

### Step 5: Add VMs to Mobility Group
*   **Action:** Add the resolved VM assets to the Mobility Group.
*   **Endpoint:** `POST /hybridity/api/mobility-groups/{groupId}/items` (or `PUT` to the group structure depending on Swagger spec).
*   **Payload Construction:**
    The body will likely require an array of "items". Each item represents a VM and must include:
    *   `inventoryItem`: The source VM ID resolved in Step 3.
    *   `migrationType`: From CSV (mapped to API enum, e.g., `BULK_MIGRATION`).

### Step 6: Configure Migration (Mapping)
Adding the VM is not enough; it must be configured (validating the target resources).
*   **Action:** Apply the destination mappings (Compute, Storage, Network) to the specific Mobility Group items.
*   **Endpoint:** `PUT /hybridity/api/mobility-groups/{groupId}/items/{itemId}` (Iterate through items or use a bulk config endpoint if available).
*   **Payload:**
    *   `destinationComputeId`: Resolved ID from Step 3.
    *   `destinationDatastoreId`: Resolved ID from Step 3.
    *   `networkMappings`: Array mapping Source Network ID (found during VM lookup) to Destination Network ID (resolved in Step 3).
    *   `migrationOptions`: Objects for `upgradeTools`, `removeIsos`, etc.

### Step 7: Validation
*   **Action:** Trigger a validation check to ensure the migration is viable (no ISOs attached, hardware version compatible, etc.).
*   **Endpoint:** `POST /hybridity/api/mobility-groups/{groupId}/validate`

## 4. Implementation Guidelines for the Agent

1.  **Swagger Discovery:** The agent should check the `/hybridity/docs` or `api-explorer` definitions specifically for the `MobilityGroup` model to confirm exact field casing (e.g., `mobilityGroupId` vs `id`).
2.  **Batching:** If the CSV contains 50+ VMs, ensure the API calls are batched if the endpoint limits payload size, though Mobility Groups are designed to handle waves of migrations.
3.  **Error Handling:**
    *   **Lookup Failure:** If `dest_network` "VLAN-100" is not found in the destination, log a specific error: "Target network 'VLAN-100' not found in remote site inventory."
    *   **Validation Errors:** After Step 7, if the API returns validation warnings (e.g., "CD-ROM connected"), parse and display them to the user.
4.  **HCX 4.11 Specifics:**
    *   Use **V2 APIs** where possible for retrieving status/summary (`/hybridity/api/v2/mobility-groups/...`) as they provide better state management than the legacy V1 endpoints.

## 5. Output Expectation
The CLI tool should output a summary:
```text
Successfully created Mobility Group: "Wave-1-Finance"
Details:
 - Added 5 VMs
 - Configured Migration Type: Bulk
 - Target Network: db-segment-1 (dvportgroup-55)
 - Validation: Passed
Ready to start migration via UI or execute start command.
```
